## 2. Goal, scope and GAP-018 dependency

**[SPECYFIKACJA]** GAP-019 provides controlled literary translation from a *durably approved* SourceMaster into at least en-US and en-GB. Translation does not start on Source creation. An authenticated explicit operator/user command is required for each locale. Drafts, chapter files, an unpromoted ManuscriptVersion, CandidateMaster and QA ACCEPT cannot serve as the official origin. No translation step may mutate SourceMaster, its manuscript, Book Bible or Canon.

**[REKOMENDACJA]** Start resolves `current_source_master(repository)` and pins its exact `project_id`, `book_id`, `source_master_id`, `version`, `artifact_ref`, **artifact SHA-256 as `source_master_hash`**, approval and sealed manuscript identity. It loads and verifies the linked ManuscriptVersion to obtain `source_language`, ordered chapter identities and exact hashes. Any mismatch, unavailable commit/approval, missing Bible decision or changed current Source before the initial intent is recorded blocks start. After intent, recovery uses the pinned Source; it never silently rebinds to a new one. A historical Source may be read, but creating a new current translation from it requires an explicit reconciliation operation rather than an ordinary start.

Out of scope: KDP/publishing and Etap 17, full UI Etap 18, multi-project scheduler Etap 19, Etap 20 hardening, AgentCritic integration, Source retcon or changes to frozen GAP-017/GAP-018. Phase 1 changes no production code, endpoint or schema.

## 3. Translation Bible and decision authority

**[REKOMENDACJA]** A `TranslationBibleVersion` is an immutable project-owned record with `schema_version`, `translation_bible_id`, `project_id`, `book_id`, `source_master_id/version/hash`, `target_locale`, `version`, `parent_bible_id?`, `decision_entries[]`, `artifact_ref`, `artifact_hash`, `created_at`, `created_by`, `approval_ref/hash?` and canonical `bible_hash`. Every translation version binds one exact Bible version/hash. An empty but explicitly created and versioned Bible is valid when no decisions are needed; an absent Bible is not silently substituted. This makes the GAP-019 binding stronger than Canon §67's permissive “may have” and does not change that authority.

Each decision entry has stable ID, kind, source form/semantic reference, approved target form or rule, locale, scope, status, author/actor and provenance. Supported kinds cover proper names, terminology, organizations/titles/technologies, locked terms and forbidden substitutions, do-not-translate, transliteration, idiom/register, dialogue, character voice, literary style, units/formats/local conventions and localization decisions. A rule may cite Source or Canon snapshots but grants no authority to change them. Contradictory active locked rules block the Bible version rather than selecting one silently.

Deterministic extraction of names, source spans, hashes and exact repeats produces *observations*, not approvals. Model output can create a *proposal* with invocation provenance. Only an explicit authorized user decision, or a previously approved deterministic policy that identifies the exact scope and value, creates a durable binding decision; a model cannot overwrite it. Manual edits create a new version and invalidate affected translation/QA as specified below. Preserve old versions. Translation Bible approval is distinct from final locale Master approval; neither is inferred from model agreement, QA ACCEPT or an operator merely starting a run.

## 4. Immutable translation lineage and locale isolation

**[REKOMENDACJA]** Every `TranslationRun` intent binds `project_id`, `book_id`, exact Source ID/version/hash, source language, target locale, Bible ID/version/hash, translation policy ID/version/hash, request/operation ID and hash, expected locale head, actor/time, ContextPackage refs and execution provenance. Supported targets initially `en-US` and `en-GB`; locale is immutable in a run and all child records. A `TranslationVersion` has stable ID/version, parent version ID?, run ID, Source and Bible bindings, ordered unit refs/hashes, assembled artifact ref/hash, status and created time. It is append-only. New Source, new Bible, intentional retranslation and targeted revision create new records; none rewrite earlier text.

Each `TranslationUnitVersion` binds exact SourceMaster, the verified sealed manuscript and chapter ID/version/artifact SHA-256/text SHA-256, a stable source paragraph/scene/semantic-segment ID or deterministic UTF-8 span with start/end and span SHA-256, target locale, Bible hash, policy hash, target span/artifact hash, parent unit version?, ContextPackage hash and invocation refs. An ordered manifest pins unit coverage and assembly policy. Mapping is many-to-many where needed; it never assumes one sentence to one sentence. Empty/duplicate/gapped required source coverage blocks candidate creation unless a documented non-translated element is in the approved Bible. A 200k+ word Source is processed in bounded units with relevant neighboring context, global Bible/terminology/voice references and chapter/whole-book reduction. No single prompt is allowed to contain the full book.

`en-US` and `en-GB` have independent run IDs, unit/version IDs, Bible heads, terminology decisions, QA, Candidate, approval, Master and current-head CAS. Both originate directly at the exact SourceMaster; en-GB never derives from en-US or vice versa. Project/book/locale are validated at every lookup, request, artifact path and recovery boundary. A locale-neutral deterministic observation may be copied only as a cited input, not shared mutable translation authority. Series data may be read only under existing verified Series access and may not become a cross-project translation cache.

## 5. Translation QA, revision and final authority

**[REKOMENDACJA]** Define a separate immutable `TranslationQAReport` rather than extending frozen GAP-017 `EvaluationRecord(QUALITY)`. It binds project/book/Source hash, locale, TranslationVersion and artifact hash, Bible hash, policy/criteria hash, coverage manifest, ContextPackage and model invocation refs, `execution_status`, `validation_status`, `quality_decision?`, findings, evidence refs, report hash and optional `reevaluation_of`. `BLOCKED` means unmet prerequisite, incomplete execution/coverage, invalid output or unverifiable provenance and has **no** quality decision. `ACCEPT`, `REVISE`, `REJECT` are quality decisions only for completed, valid, fully covered reports. Reuse P20 mechanics where contracts permit; do not change the GAP-017 record kind.

Required checks: semantic fidelity; omissions, additions and mistranslations; terminology, names and entities; Canon and Bible compliance; style, voice and dialogue; target-language naturalness and locale correctness; cross-chapter continuity and formatting-sensitive content. Findings carry criterion, severity, exact source and target unit/span refs and hashes, evidence, affected scope and repair action. Deterministic checks are labeled local, with no invented model/provider. Source-aware fidelity and target-only naturalness may be separate evaluations, as Architecture §123 allows. Hierarchical unit/chapter/book reduction requires full coverage and preserves blocking findings; a global average cannot erase an omission, Canon breach or critical chapter defect.

`REVISE` identifies affected units, creates a child TranslationVersion with unchanged, hash-verified unaffected units and new versions only for affected units, then runs **new full required QA coverage** over the assembled version. `REJECT` produces no locale Candidate or Master. A valid `ACCEPT` may create an immutable locale Candidate bound to exact translation/QA/Source/Bible hashes. The final `TargetMaster` requires a **separate explicit user acceptance** of that exact Candidate, with authenticated actor, durable approval/rejection receipt, pinned expected locale Master head and CAS. A model, run completion, Translation QA ACCEPT, or operator technical retry cannot provide this authority. A rejection cannot be reused as approval. No accepted artifact is overwritten; a manual edit makes a new auditable version requiring affected QA again.

## 6. Source and Bible staleness

**[REKOMENDACJA]** Historical records remain readable. Effective `STALE_AGAINST_SOURCE` is determined by comparing each translation's pinned Source ID/version/hash with the verified current Source head, and is durably reflected in status/receipt when observed; a new Source never rewrites old records or automatically starts translation. A stale translation cannot create a new Candidate or Master or be presented as current for the new Source. Explicit new translation/reconciliation starts from the new Source with new request/lineage. A final historical Master retains its audit history but is marked stale relative to current Source.

A new Bible version leaves prior versions intact. A translation pinned to an older Bible is `STALE_AGAINST_BIBLE` for new Candidate/Master promotion if the current approved Bible head changed; affected units require explicit reconciliation and fresh QA. Existing historical Master is not silently rewritten. A Bible change scoped to a different locale does not invalidate this locale. Source staleness takes precedence in eligibility when both apply. Neither status grants authority to edit Canon or Source.

## 7. Storage ownership, idempotency and recovery

**[DOWÓD]** Schema 7 offers generic `project_metadata(key,value)` but the durable GAP-018 record kinds and head/CAS methods are explicitly restricted to GAP-018. Generic metadata upsert alone has no translation-specific immutable-record validation, per-locale head invariant, request conflict rule or indexed lineage. Treating GAP-018 record kinds as GAP-019 storage would violate their frozen meaning.

**[REKOMENDACJA]** Schema 7 is sufficient to *read Source and store existing project metadata*, but not sufficient **as currently implemented** for the required enforceable translation contract. Phase 2 should make the smallest controlled project-only migration, proposed `project.db` **7→8**: one immutable `translation_records` table keyed by project/book/locale/kind/record ID with canonical payload hash and schema/owner validation; one `translation_heads` table keyed by project/book/locale/head kind for Bible, translation Candidate and final TargetMaster with ID/version/hash and compare-and-swap; one `translation_request_receipts` table keyed by project/book/locale/operation kind/request ID with immutable request hash, pinned bindings, state and result reference. Exact SQL/index layout is Phase 2 implementation detail, but these uniqueness, immutability and CAS invariants are frozen. Project artifacts remain under `StorageResolver` project root via existing project artifact boundary, with confined paths and SHA-256. Do not modify `series.db` or system DB. Controlled migration preserves v7 rows and Memory Ledger; tests cover v7→8, reopen, interrupted migration and legacy projects. If Phase 2 proves equivalent guarantees in existing v7 primitives without weakening validation, document that evidence before any change to this proposed migration; do not raise schema merely for convenience.

An idempotency key is `(project_id, book_id, target_locale, operation_kind, request_id)`. The stored canonical request hash includes actor/authority where relevant, pinned Source/Bible/policy, expected locale head and operation-specific input IDs. Same key and same payload returns the original durable receipt/status; same key and changed payload is a conflict. A retry never creates a second version or approval. Intentional retranslation, targeted revision, QA reevaluation, new Bible and new Source each need a distinct operation kind/new request and explicit parent/binding; none are technical retries. Different requests racing on one locale head use `BEGIN IMMEDIATE` and exact expected-head CAS; one wins and the loser becomes a durable conflict. A later replay returns its historical receipt without moving current heads. Do not hold DB transactions during model calls.

An operation persists its immutable intent and pinned bindings before model execution. Unit artifacts and model responses have deterministic identities/hashes and provenance; completion is recorded only after verified artifacts and F-004 commit. F-004's existing project artifact protocol and Memory Ledger events must explicitly cover GAP-019 operation types; adding an operation type is not equivalent to bypassing the Ledger. Domain record/head commit follows a verifiable cross-store receipt, in an idempotent transaction. Recovery handles interruption at start, after a subset of units, after a model call, during QA, after file/F-004 commit but before domain commit, and after reopen. It reloads exact intent, checks project/book/locale/Source/Bible/policy/ContextPackage/invocation and artifact hashes, resumes only missing work and fences stale workers. It cannot change locale or Source, fabricate Bible decisions, regenerate an already persisted response as if identical, auto-ACCEPT QA or auto-approve a Master. Missing/tampered evidence yields `NEEDS_INTERVENTION`, not a silent fallback. Technical `RECOVERY_REQUIRED` remains distinct from quality `BLOCKED`.
